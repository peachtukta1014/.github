# System protocol design

A protocol is not code. It is the answer to five questions that must not be ambiguous:

1. **Who owns each fact?** (authority — exactly one writer per fact)
2. **What states exist, and which are terminal?** (state machine)
3. **How does a message find its reader?** (addressing + delivery)
4. **What happens when the other side is dead?** (failure path)
5. **What counts as "done"?** (evidence contract)

If any of the five is unstated, the system will invent an answer at runtime — usually
a duplicate, a phantom record, or a silent drop. This skill makes you state them first and
verify them after.

## Before designing: name the existing facts

Never start from a blank page. Write the matrix first, because most "protocol bugs" are two
writers on one fact.

| fact | authority (the only writer) | readers | deposit point |
|---|---|---|---|
| the work itself, owner, ACK | board / work-order store | lanes, owner | board API + pad |
| completion of a work order | pad `completed_units` | room, reports | pad file |
| team conversation + announcements | room (append-only log) | all lanes, owner | `_mesh/rooms/<room>.jsonl` |
| system events (no work order behind them) | event ledger | the addressed lane | `_mesh/events/<id>.json` |
| durable decisions / conventions | SSOT index + the one doc per topic | everyone | repo |

Rule: **one fact, one writer, one deposit point.** A second writer is a bug even when it is
convenient. Projections (a `done` line in the room) are allowed only if they are generated by
the authority's own close path and are clearly marked as projections.

## The five decisions

### 1. Authority
- Say out loud which store wins when two disagree. Typical answer: the work store wins over
  the room; the ledger wins over the announcement.
- Never let a lane write another lane's state to "help". It may only send a request.
- Cross-store references must be by durable id (`WO-…`, `evt-…`, commit sha), never by text.

### 2. State machine
Write it as an arrow list with the actor for each edge:

```
new --(addressed lane acts)--> acked --(lane finishes)--> done        (terminal, idempotent)
new --(lane decides no action needed)-------------------> done
done --(any repeat)--> done            # prints ALREADY done, writes nothing
```

- Choose the smallest set of states that answers "may anyone still act?" If a state cannot
  change a decision, delete it.
- Terminal states must be **idempotent**: a second close returns the original timestamp and
  actor, and must not append a second line, notification or unit.
- Every state change records `who`, `when`, `why` (result) and `how verified` (evidence).

### 3. Addressing and delivery
- Addressing is explicit: `to: <lane>|all`, plus optional mentions (`@lane`) that are resolved
  **at write time**, so a reader never re-parses prose to find out if it was meant.
- Pick delivery per receiver: **pull** (cursor/watermark, safe, testable) or **push** (SSE, WS,
  webhook — fast, unverifiable on its own). Ship pull first; push is an accelerator, not the
  source of truth.
- A cursor is `{last_id, at}` per reader, stored server-side; advancing is part of the read, and
  `--no-advance` exists for inspection. Without a cursor, every reader re-processes history.
- Never acknowledge by "read count". Ack by id.

### 4. Failure path
Answer these before shipping:

| if this dies | what must still be true |
|---|---|
| the notifier / push channel | the record exists; pull still delivers it later |
| the receiver | the item stays `new`; nothing is marked done on its behalf |
| the room | the close still succeeds; announcement is retried or dropped with a note |
| the store write | the caller gets an error, not a silent success |

Projection writes are **best-effort but logged**: a failed projection must never roll back the
authoritative state, and must never be silently invisible either.

### 5. Evidence contract
Completion is not "I saw it". Define per kind:

- `done` requires `result` (what was checked) + `evidence` (how it was checked: id, timestamp,
  command output, sha, path).
- A `done` without evidence is a **claim**; readers must be able to tell the difference. Encode
  it: reject it, or mark it `claimed: true`.
- `decision` from someone who is not the owner is a `note`.
- Status reported to a human must quote the artifact (id/line/commit), not a summary of it.

## Design review checklist (run before you build)

- [ ] Authority matrix written; no fact has two writers.
- [ ] State machine drawn; terminal states idempotent; retries cannot duplicate.
- [ ] Every message has a durable id at creation time.
- [ ] Addressing resolved at write time; readers never parse prose.
- [ ] Pull path exists and is tested; push is additive.
- [ ] Cursor/watermark per reader, and a way to inspect without advancing.
- [ ] Failure table filled for notifier, receiver, projection target, store.
- [ ] Evidence contract written per kind, with an example of a rejected close.
- [ ] One deposit point per fact; projections labelled as projections.
- [ ] Docs split: one page = why/obligations (the contract), one page = how to use (commands).
      Register both in the SSOT index; nothing restated in two places.

## Anti-patterns (each one seen in production)

| anti-pattern | symptom | fix |
|---|---|---|
| phantom record to satisfy a close path | fake `WO-…` rows nobody dispatched | give the object its own ledger + state machine |
| close on read | work marked done because someone opened it | separate `acked` from `done`, require evidence |
| second writer "to help" | duplicate units, conflicting status | one writer; others send requests |
| notify without a cursor | same alert every 60 s | per-reader cursor, `notified_at` stamp |
| push-only design | alerts lost when the socket dies | pull is the truth, push is a hint |
| id derived from content | can't trust a reference after an edit | id at creation, immutable |
| docs restating the same rule | CI drift, contradictory pages | one SSOT row + pointer |

## Worked example (2026-11-18, this VM)

Problem: system events arrived with ids like `evt-...`, but the only close path was a work
order, so lanes answered `ERR job not found in pad` and events never closed. Someone's
temptation was to invent a fake `WO-`.

Design actually shipped:
- fact "system event exists" → ledger `_mesh/events/<id>.json`, written at the door
  (`services/hq-core/src/http.js`, best-effort spawn, never blocks delivery)
- states `new → acked → done`, `done` idempotent ("ALREADY done <id> at <ts> by <lane>")
- addressing `--lane`; delivery pull (`mesh_event inbox --lane L`, cursor in
  `_mesh/event_cursors/`) **plus** an announcer (`mesh_event_notify.py`) on a systemd timer
  that posts one `@lane` line into the room and stamps `notified_at`
- failure: room down → ledger write still succeeds, announcement retried next round
- evidence: `done` needs `--result` + `--evidence`; contract lives in `system/EVENT_LEDGER.md`
  (SSOT #29), room side in `ROOM_PROTOCOL.md` (#28)
- verification: dispatched at 05:48:16, announced by the timer at 05:48:31 with no manual run;
  repeat close printed `ALREADY done`; `list --status new` = empty

## Working style

1. Write the five answers in the doc **before** the code, and keep the doc at one canonical path.
2. Ship the pull path first, verify with ids and timestamps, then add push.
3. Every claim of "works" needs a fresh command output in the same breath — no extrapolation
   from "it should". See `dev-verification-gate`.
4. When a protocol changes, update the SSOT row and regenerate anything generated
   (routes index, pins) in the **same** commit, or the next CI run will fail.
